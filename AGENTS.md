# Постоянные правила разработки сайтов и веб-приложений

- Перед работой читай применимые инструкции проекта (AGENTS.md и явно связанные документы), существующий PROJECT_CONTEXT.md и затронутый код. Определи стек, архитектуру, фактические версии зависимостей по lock-файлам/установленным пакетам и команды проверок. Диапазон в package.json не считай точной установленной версией.
- Сохраняй согласованный визуальный стиль, архитектуру, контракты и существующее поведение, кроме явно запрошенных изменений. Не меняй стек и не выполняй несвязанный рефакторинг.
- Выбирай навыки по задаче и читай их SKILL.md: frontend-design для дизайна/создания UI; vercel-react-best-practices только для React/Next.js и только применимые к их версии правила (не переносить Next.js/DOM-правила на React Native); web-design-guidelines для проверки UI и доступности; backend-quality для серверных изменений; security-best-practices для безопасной разработки и security-review поддерживаемых Python, JavaScript/TypeScript, Go; playwright для проверки работающего сайта через браузер; responsive-visual-qa для адаптивной визуальной проверки. Не загружай весь набор для каждой задачи.
- Пиши новый код с безопасными настройками по умолчанию. Проверяй данные и доступ на сервере, не допускай секретов в клиентском коде и логах. Масштаб проверок соразмеряй изменению; полный аудит безопасности не запускай без задачи на аудит.
- При работе с API библиотек, их настройкой и зависящим от версии кодом используй Context7: сначала определи название библиотеки и её версию из проекта, затем resolve-library-id и query-docs с найденным ID и нужной версией. Если точной версии в индексе нет, Context7 недоступен или ответ неполон, используй официальную документацию разработчика для нужной версии и укажи ограничение. Не выдавай документацию latest за проверенную совместимость. Не отправляй секреты и приватные данные в поисковые запросы.
- После существенных изменений интерфейса проводи визуальную проверку телефона, планшета и компьютера по responsive-visual-qa: 360, 390, 768, 1024, 1440 CSS px и промежуточные размеры, ключевые состояния и взаимодействия. Просматривай скриншоты. Честно различай эмуляцию и настоящее устройство; не заявляй о проверке Safari/iPhone без такой проверки.
- После изменений запускай подходящие тесты, lint, проверку типов и сборку, если они относятся к задаче и доступны. Добавляй содержательные проверки критичных сценариев. В результате указывай, что действительно проверено, что не запускалось и почему.
- Не меняй рабочий публичный сайт без явного указания пользователя. Это относится к production deploy/publish, изменениям публичных данных, конфигурации и production-миграциям. Разработка и проверка локальной/изолированной тестовой версии не означает разрешение менять production.
- В длительных проектах поддерживай краткий PROJECT_CONTEXT.md в корне: принятые решения, выполненное, открытые проблемы и следующий шаг. Читай его при продолжении работы и обновляй после значимых этапов. Не храни секреты, токены, персональные данные и полные логи; ссылайся на существующие подробные документы вместо дублирования.

Существующий ~/.codex/instructions.md сохранён как отдельный прежний документ. Эти правила не перезаписывают его и не заменяют инструкции конкретного проекта.

## Границы изменений и визуальная проверка

- Выполняй только запрошенные изменения.
- При исправлении одного элемента сохраняй оформление и поведение остальных.
- Не меняй соседние кнопки, отступы, размеры, тексты и адаптивную сетку без необходимости для задачи.
- Перед изменением общих компонентов и стилей проверяй, какие страницы они затрагивают. Предпочитай локальное исправление.
- Не проводи попутный рефакторинг и редизайн.
- Перед завершением просматривай diff и удаляй собственные изменения, не связанные с задачей.
- Для визуальных исправлений сравнивай результат до и после при одинаковой ширине экрана: проверяй целевой элемент и соседние блоки на телефоне и компьютере.
- В отчёте указывай, что изменено и что фактически проверено.
