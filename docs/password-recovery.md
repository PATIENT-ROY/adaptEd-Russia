# Восстановление пароля: проверка и исправление, 23.10.2026

## Подтверждённая причина

В `client/src/app/forgot-password/page.tsx` отправка была заглушкой `setTimeout(1000)` без API-запроса. Кнопка повторной отправки только переключала `isSubmitted` в false. В `server/src/api/auth.ts` отсутствовал публичный обработчик восстановления.

На опубликованной странице воспроизведено показанное пользователем поведение: успех появился при нуле попыток POST к auth API; повторная отправка вернула поле email. Для этой проверки все не-GET/HEAD запросы блокировались браузером, использовался синтетический адрес `.invalid`; письма не отправлялись, production-данные не менялись. Ошибка `/api/auth/login` не является подтверждённой причиной этого сбоя.

## Исправление и контракт

- Форма и «Отправить ещё раз» ожидают `POST {API_BASE_URL}/auth/forgot-password` с `{ email }`. Непосредственный fetch соответствует существующему set-password; используется тот же `NEXT_PUBLIC_API_URL`. HTTP-ошибка показывает существующее сообщение ошибки; при resend выполняется новый запрос. CSS и соседние кнопки не менялись.
- Backend нормализует email, ищет пользователя, создаёт 32 случайных байта и сохраняет SHA-256 в существующей `PasswordSetupToken`. Миграции не нужны.
- Письмо отправляется через существующий `sendEmail`, который делает HTTPS POST в Resend с ключом `RESEND_API_KEY` и отправителем `EMAIL_FROM`. Вызов awaited, повторные попытки используют стабильный idempotency key без исходного токена. Кнопка resend создаёт новый токен и отдельную отправку.
- Ссылка: `${APP_BASE_URL || CLIENT_URL}/set-password?token=…`; в development без настройки — localhost:3000. В production отсутствующий URL, HTTP, localhost, credentials, query/hash и неверный базовый path отклоняются. Никакой адрес из HTTP Host не используется.
- Срок — 1 час. Существующий обработчик установки пароля атомарно помечает токен использованным под блокировкой пользователя, меняет пароль, повышает tokenVersion и отзывает остальные ссылки. При запросе письма пароль и действующие сессии не меняются. Отказ отправки отзывает созданный токен.
- Для валидного email публичные статус и JSON одинаковы при существующем/неизвестном аккаунте, отказе Resend, отсутствии конфигурации и внутренней ошибке. Публичный ответ подтверждает обработку запроса, а не доставку.
- Лимит восстановления — отдельное хранилище 10 запросов / 15 минут на IP при включённом ENABLE_RATE_LIMIT; попытки входа им не расходуются.

## Безопасные серверные события

- `password_reset.email_accepted`: provider, attempts, случайный requestId. Значит принятие API Resend, а не доставку в ящик.
- `password_reset.email_failed`: provider, attempts, HTTP status (если есть), reason (`missing_configuration` / `provider_failure`), requestId.
- `password_reset.failed`: stage (`lookup`, `configuration`, `token`, `email`), requestId.
- `password_reset.token_cleanup_failed`: requestId.

Не логируются email, пароль, ключ, токен, URL восстановления, необработанные тела ответов провайдера и тексты исключений, которые могут содержать эти данные.

## Что проверено

- 10 HTTP-тестов реального Express router с подменёнными Prisma и Resend: ожидается провайдер, успешная отправка, отказ 403, отсутствие ключа, неизвестный email, новая отправка, просрочка, однократность и отзыв остальных ссылок, неверный ввод, сетевой отказ с retry, неверный URL. Проверяется отсутствие чувствительных значений в логах.
- 2 интеграционных сценария на отдельной временной PostgreSQL: сохранение настоящего токена, успешное восстановление, два одновременных сброса дают ровно один успех, replay отклонён; просроченный токен не меняет пароль. Resend подменён. Только синтетические аккаунты в этой БД.
- Существующие 5 auth-security проверок также прошли на этой БД, включая конкурентную одноразовость и отзыв JWT.
- 4 Playwright-теста desktop/mobile: исходная отправка, resend, ожидание API, отсутствие ложного успеха при HTTP-ошибке и повторной ошибке. Все API перехвачены; реальных писем нет. Скриншоты успеха просмотрены: `output/playwright/password-recovery-success-*.png`.

## Ограничения и production

Локальный `server/.env` не содержит RESEND_API_KEY и EMAIL_FROM. Это проверка наличия переменных в файле, не работающем production-процессе. Локальный backend на 3003 при диагностике не был запущен. Production-логи, runtime environment, действительность ключа, его права/привязка к домену и статус домена в панели Resend недоступны в этой сессии.

Перед отдельной разрешённой публикацией требуется проверить в фактически работающем backend:

1. Наличие действующего RESEND_API_KEY с правом отправки и EMAIL_FROM; секреты не выводить.
2. APP_BASE_URL/CLIENT_URL указывает на HTTPS frontend AdaptEd Russia; NEXT_PUBLIC_API_URL в собранном frontend указывает на нужный backend.
3. Домен EMAIL_FROM подтверждён в том же аккаунте Resend. Требование подтверждения домена описано в [официальной документации Resend](https://resend.com/docs/dashboard/domains/introduction); формат отправки — [Send Email API](https://resend.com/docs/api-reference/emails/send-email).
4. Сопоставить серверное событие и запись Resend; отдельно проверить delivery/bounce и получение в ящике.

**Реальная доставка НЕ проверена.** Для неё нужен согласованный тестовый адрес владельца и доступ к настройкам/логам нужной среды. Письма пользователям не отправлялись, пароли существующих пользователей не менялись. Публикации, изменений production environment/данных/домена не было.

Context7 не предоставил привязанные к Prisma 5.22 материалы (выдача содержала API более новых версий). Новый код следует уже используемым в проекте операциям Prisma; совместимость проверена установленным Prisma 5.22.0, компилятором и фактическими PostgreSQL-тестами, без утверждения о совместимости по документации latest.
